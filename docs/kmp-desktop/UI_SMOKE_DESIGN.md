# In-app UI smoke mode — design (not built)

Status: Windows and Linux engineer — done: the one-page design for Atlas (ANSWER 005 item 5) — left: Atlas's answer,
then the build. Nothing is built. Code facts are read from `multiplatform`; **[guess]** marks what the first spike must
confirm.

**What it is:** `Komikku --ui-smoke=<report dir>` starts the real app (same `main()` path, DI, scheduler, window) on a
fresh temporary data folder with a generated fixture, runs a fixed script through the app's own navigation, saves a
PNG of the window after each step, writes a report and exits non-zero on the first failure. Compiled in, inert without
the argument, no network, never the user's data folder. CI runs it with the packaged launcher on Linux, Windows and
macOS and uploads the report folder.

## 1. Where the script lives

- **Package `app.komikku.desktop.smoke` in `desktopApp/src/main`** (it must be in the packaged app; nothing in `:app`,
  `:app-shared` or any file `master` owns). Files: `UiSmoke.kt` (argument, setup, exit code; parallel to
  `selftest/DesktopSelfTest.kt`), `SmokeDataFolder.kt` (the guard), `OfflineNetwork.kt`, `SmokeFixture.kt`,
  `SmokeDriver.kt` (window, screenshots, input, waiting), `SmokeScript.kt` (the steps), `SmokeReport.kt`.
- **Entry:** one branch in `main()` before anything touches `DesktopDirs` (like `--self-test`):
  `if (UiSmoke.isRequested(args)) exitProcess(UiSmoke.main(args))`. `UiSmoke.main` prepares the folder, sets
  `komikku.dataDir`, then calls the normal start-up, which `main()` would move into `runKomikku(app hooks)` (a small
  refactor of `Main.kt`; the hooks are "after DI init" and "after the window shows", nothing smoke-specific).
- **Fixture, generated by code, not a binary resource:** `SmokeFixture.write(<data>/storage/local)` (the local source's
  folder, `DesktopStorageFolderProvider` + `StorageManager`) writes `Smoke Fixture & Co/` with `details.json`, a
  `cover.png` and `Chapter 1/001.png…003.png` (Java2D, 600 × 900, a large page number and a distinct colour per page so
  page turns differ in the screenshots), about 20 KB. Optional `Chapter 2.cbz` for the archive path. Deterministic, no
  binary in git; a zipped resource would do the same if Atlas prefers real files.
- **Unpacked into the temporary data folder only**, deleted at exit (`--ui-smoke-keep` keeps it for debugging).

## 2. Reaching the navigator without test code in screens

- **No smoke branch in any screen and no coordinates.** The driver uses what the app already exposes, the same calls
  the click handlers and shortcuts make:
  - tabs: `DesktopShortcuts.handler(SelectTab(i))`, the route of Ctrl+1…5 (`HomeShell`);
  - stacks: a small **`NavigatorRegistry`** (production, not smoke): `AppNavigatorHost` (`:app-shared`, not on `master`)
    registers its navigator under its root screen's key through a `CompositionLocal` that `KomikkuApp` provides
    (`null` in tests and on Android, then nothing happens). The driver pushes the same `Screen`s the UI pushes
    (`SettingsCategoryScreen`, `CatalogueScreen(LocalSource.ID)`, `MangaDetailsScreen(id)`). The registry is also what
    a notification click or the tray needs later ("open Updates");
  - reader and lock: `ReaderLauncher.open(mangaId, chapterId)` (what a chapter click calls), `DesktopAppLock.enable` /
    `lockNow` (Security settings' calls);
  - **real input where the app has keyboard input:** AWT `KeyEvent`s dispatched to the window's `SkiaLayer` component
    (page turn with Page Down, the PIN and Enter on the lock screen, Escape to close the reader). Dispatched directly
    to the component, so no OS focus, no `Robot`, no permission.
  Click handlers stay covered by the headless Compose UI tests (about 90 classes); the smoke mode proves the packaged
  app on a real window system.
- **Steps are data:** `Step(name, action: suspend SmokeDriver.() -> Unit, until: SmokeDriver.() -> Boolean,
  timeout)`. `until` reads observable app state: the tab navigator's current tab, a navigator's `lastItem`, the
  database (fixture entry and chapters present, `lastPageRead == 1` after the page turn, as `ReaderUiTest` checks),
  `DesktopAppLock.locked`; text on screen through the in-process accessibility tree of the `ComposeWindow`
  (`accessibleContext`, Compose's semantics: e.g. "1 / 3") **[guess: complete enough in-process; else a read-only
  `StateFlow` on the existing holder, e.g. `ReaderLauncher`]**.
- **Waiting:** the driver runs on the window's coroutine context (EDT). After `until` holds: wait until every
  `Recomposer.runningRecomposers` is idle or 2 s passed (spinners never idle; recorded, not failed), then render a
  frame (`SkiaLayer.renderImmediately()`) and take the screenshot.
- **Script:** `01-library` (empty) · `02-updates` · `03-history` · `04-browse` · `05-more` · `06-settings` (Appearance)
  · `07-catalogue` (local source lists the fixture) · `08-details` (2 chapters synced) · `09-reader` (page 1 of 3) ·
  `10-page-2` (Page Down; `lastPageRead == 1`) · `11-locked` (enable PIN, `lockNow`) · `12-unlocked` (PIN typed) ·
  `13-close` (Escape, close request; the app's normal shutdown, exit code checked). Proposed extra for Linux CI:
  `14-new-chapter` (add to library, add `Chapter 2`, run the library update: "New chapters found" posted through the
  system notifier, seen by `dbus-monitor`; WINDOWS_LINUX_TEST_PLAN.md section 5).

## 3. Screenshots on each system

- **`SkiaLayer.screenshot()`** (Skiko 0.150.2, public, `javap`-checked: it draws the layer's last recorded picture into
  a raster `Bitmap`), PNG through Skia's encoder. The layer is found by walking the `ComposeWindow`'s components.
  Independent of the render API (Metal, Direct3D, OpenGL, software) and of the OS: **no Screen Recording permission on
  macOS, no X screen grab on Linux**; in-window dialogs and menus are on the same canvas **[guess: also in this Compose
  version's layer mode; separate-window popups would be missing]**. Device pixels (2× on Retina).
- **`java.awt.Robot` only as an optional cross-check** (whole screen: desktop, notification popups): needs the Screen
  Recording permission on macOS (an unsigned app would prompt and block, so off there) and a display on Linux.
- **CI:** Linux `ubuntu-24.04`: Xvfb + openbox as in section 4 of the test plan; Skiko on Mesa llvmpipe or software
  **[guess]**, both fine for the screenshot. Windows `windows-2022`: needs the runner's interactive desktop so the
  window renders **[guess]**; no frame within the timeout is reported as "window never rendered", itself the finding.
  macOS runners (VMs, maybe no Metal): Skiko falls back to software **[guess]**; no permission needed.

## 4. No network, never the user's data

- **Network:** before DI init a process-wide `ProxySelector` records every URI and routes it to a closed port on
  `127.0.0.1`; OkHttp and `URLConnection` ask it for every connection (also FlareSolverr's own client). After DI init
  `NetworkHelper` (open since SY) is replaced by one whose `client` has a first interceptor that fails every call and a
  `Dns` that throws. Preferences preset: update checks, scheduled library updates and backups off. **Any attempt fails
  the run** (listed in the report). Optional on Linux CI: run inside a network namespace **[guess]**.
- **Data folder guard (`SmokeDataFolder`):** a new `Files.createTempDirectory("komikku-ui-smoke-")`, owner-only;
  refused (exit 2, before DI) when it equals, contains or lies inside the OS default data folder
  (`DesktopDirs.resolveDataDir` without override) or a `komikku.dataDir` given on the command line, or is not empty.
  After setting the property, `DesktopDirs.dataDir` must resolve to it, else exit 2. Never takes a folder argument.
  Runs beside a user's Komikku (the single-instance lock is per data folder, ANSWER 005 item 4).
- **Tests (`:desktopApp:test`):** `OfflineNetworkTest`: `NetworkHelper.client`, a fresh `OkHttpClient()` and
  `URL.openConnection` against a local `MockWebServer` all fail, the server sees 0 requests, the recorder lists 3.
  `SmokeDataFolderTest`: each refusal case; a child JVM (as `DesktopSingleInstanceTest` does) with `user.home` and
  `komikku.dataDir` pointing at marked folders, checked untouched afterwards. `SmokeScriptTest`: the same step list run
  headless through `runDesktopComposeUiTest` with a test driver (`captureToImage` for screenshots), so the script is
  checked on every test run, not only in CI. CI: the report must say "network attempts: 0" and the default data folder
  must not exist after the run.

## 5. Report, exit codes, size

- `<report dir>/report.txt`: environment (OS, Java, Skiko render API, scale, window size, data folder), one line per
  step (`PASS 07-catalogue 812 ms 07-catalogue.png`), network attempts, last line `UI-SMOKE PASSED` / `UI-SMOKE FAILED`
  (the workflow reads only that, like the self-test). `report.json` with the same data; `NN-<step>.png`; on failure
  `NN-<step>-failed.png`, the stack trace and a copy of `komikku.log`. Exit 0 passed, 1 a step failed, 2 refused (guard),
  3 watchdog (5 min overall; the report is written before `Runtime.halt`).
- **Window size** (`SmokeWindowSize.kt`): 1280x800 where the usable screen area (without menu bar, Dock or task bar)
  holds it, else the largest window that fits with an aspect between 5:4 and 16:10, the reason on the report's
  `window size:` line (macOS runner: `1024x684, not 1280x800: the usable screen area is 1024x684`). Refused (exit 2)
  below 960x600: the details screen needs about 530 px of content height for both fixture chapters whole on screen,
  plus a title bar of up to 40 px; 960 is 600 at 16:10. `SmokeScriptTest` runs the script at 1280x800, 1024x684 and
  960x600 and checks the chapters are whole on screen.
- **Size [guess]:** about 900 lines of app code (smoke package), about 30 lines elsewhere (`main()` refactor,
  `NavigatorRegistry` hook in `AppNavigatorHost`, `KomikkuApp` providing it), about 500 lines of tests; 2–3 days for one
  engineer plus review, then CI iterations (Test and release engineer, about 40 lines of workflow per OS).
